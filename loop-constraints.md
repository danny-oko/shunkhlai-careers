## Project-specific — shunhlai-careers (Next.js 16 / React 19 / Tailwind 4)

### Never touch without asking me first
- `src/lib/api/core/*` — the transport core: `tokens.ts` (applicant **and**
  admin JWT pairs in localStorage under `shunkhlai.*`), `client.ts`, `request.ts`,
  `config.ts` (`NEXT_PUBLIC_API_URL`, `resolveBaseUrl`), `errors.ts`, `factories.ts`.
  This is auth transport. Do not "improve" token storage, rewrite refresh logic,
  rename storage keys (older builds still read them), or migrate to httpOnly
  cookies. `tokens.ts` documents that migration; it is a human decision, not a
  cleanup. The localStorage/XSS trade-off is known and accepted for now.
- `src/lib/api/auth.ts`, `account.ts`, `profile.ts`, `applications.ts`,
  `sections.ts` — endpoint bindings mirroring the Postman collection. Changing a
  path or payload shape silently breaks against the real backend, which the loop
  cannot reach and therefore cannot verify.
- `src/app/api/applicant/[...path]/route.ts` and `src/server/mock/*` — the mock
  backend standing in for the recruitment service. It mimics the real
  `{ rettype, retmsg, retdata }` envelope on the real paths. Edits here change
  what "working" means for every client call. Never make the mock accommodate a
  client bug.
- `src/components/auth/*` (`auth-form.tsx`, `session-provider.tsx`),
  `src/app/login/`, `src/app/register/` — credential entry and session context.
- `src/components/account/*` and `src/app/account/**` — real applicant PII:
  profile, family, education, experience, interests, CV files.
- `.env.example` — the documented env contract. Never add a real value to it.
- `src/lib/apply-schema.ts` — validation for real applicant PII: Mongolian
  register numbers, phone patterns, CV upload type/size limits. Loosening a
  regex or raising `MAX_CV_BYTES` is a security change, not a cleanup.
- `src/components/brand/*` — hand-built brand visuals (arc-bloom, feather-lattice,
  rise, gradient-rule, careers-hero) derived from the brandbook. These look like
  refactorable SVG/animation code. They are design decisions. Leave them alone.
- `public/brand/*` — brand assets. Never regenerate, recompress, or rename.
- `next.config.ts`, `postcss.config.mjs`, `eslint.config.mjs`, `tsconfig.json`,
  `components.json` — build and tooling config.
- `CLAUDE.md`, `AGENTS.md` — agent instructions. The loop must not rewrite its
  own orders.
- `bun.lock` — this project uses **bun**, not npm. Never run `npm install` or
  `yarn`; it will produce a second lockfile. Use `bun install` only when I ask.

### Care required
- `src/components/ui/*` — shadcn primitives, regenerated by the shadcn CLI.
  Hand-edits here get silently overwritten later. Propose a wrapper instead.
- `src/lib/jobs/*` (`service.ts`, `mapper.ts`, `filters.ts`, `types.ts`) — the
  job data layer that replaced the old `mock-jobs.ts` fixture in PR #4. The
  mapper translates backend payloads into UI types; a change here can silently
  blank fields on the careers pages rather than erroring.
- `src/app/careers/[id]/` and `src/components/apply-dialog.tsx` — the
  applicant-facing apply flow. Any change here touches a form real candidates
  submit. Human review, always.

### Keeping this file honest
- These paths describe `main` as of 2026-09-10 (after PR #4). Refactors move
  them. If a rule here names a file that no longer exists, the guard rail is
  protecting nothing — say so in `STATE.md` as a High Priority item instead of
  silently ignoring it.

### Verification for this repo
- A change is only verified if **all three** succeed:
  - `bun run test` (vitest; 51 unit tests over tokens, mapper, apply-schema)
  - `bun run lint`
  - `bun run build`
- Coverage is deliberately narrow: the transport, the job mapper, and the
  applicant schema. A change outside those three areas passes `test` without
  being tested — say so rather than implying it is covered.
- Never claim a fix works on the strength of reading the diff alone.
- If a proposed fix cannot be verified by those two commands, downgrade it to a
  report-only finding in `STATE.md` and stop.

### Scope
- This is a marketing + careers site. Prefer no change over a clever change.
- Copy, brand wording, and Mongolian-language strings are mine. Report typos;
  never silently rewrite user-facing text.

### Branch triage — this repo squash-merges
- PRs here land as **squash merges**: GitHub creates a new commit, so the
  original branch commits never become ancestors of `main`.
- Therefore `git branch --contains <sha>` and `git log main..<branch>` will
  report already-shipped work as "unmerged". That signal is **not** evidence.
- Before calling a branch unmerged, verify the *content* is absent from main:
  compare the actual files (`git diff main:<path> <branch>:<path>`), not the
  commit graph.
- Before proposing a PR from any branch, check its two-dot diff
  (`git diff --stat main..<branch>`). A large deletion count means the branch
  is stale and forked from an old point — it would revert newer work. Report
  it as a stale branch to delete; never open the PR.
- Reference case (2026-09-10): `feature/dark-mode` looked unmerged via
  `--contains`, but PR #3 had squash-merged it as `8c2e744` and the theme files
  were byte-identical to main. A PR from that branch would have proposed
  -8996 lines, deleting the landing page, account section, auth, and the
  `src/lib/api/*` layer merged in PR #4.
