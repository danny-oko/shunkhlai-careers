## Done means

Each line is true or false. No judgement calls.

**Candidate**
- [ ] `NEXT_PUBLIC_API_URL` points at `careers.shunkhlai.mn` in production
- [ ] Submitting the apply form creates a real application, confirmed in the
      recruitment system by a human
- [ ] The CV upload reaches the backend and can be downloaded again
- [ ] The whole flow completes on a 390px screen
- [ ] Every candidate-facing string is Mongolian, including errors and empty
      states
- [ ] A backend outage shows a message, not a 500

**HR / admin**
- [ ] An HR user signs in at `/admin/login` via
      `POST /api/applicant/auth/adminUserLogin`
- [ ] The admin token is kept separate from the applicant token and never
      leaks into a candidate-facing request
- [ ] HR can create, read, update and delete everything the documented admin
      API allows: company info, recruitment sliders, news, video, internship
      page and its images
- [ ] An unauthenticated request to any `/admin/**` route redirects to login
- [ ] Admin screens are responsive; a phone is a legitimate way to use them

**Quality**
- [ ] `bun run lint` enforces the rules under "Code quality bar" below
- [ ] `bun run test && bun run lint && bun run build` green in CI on every PR

## Code quality bar

Modelled on `~/Documents/pinecone-monorepo` (`.cursor/rules/eslint.mdc` and
`tools/eslint-rules/`), adapted for a single app.

- `max-lines`: **180** per file — pinecone uses 160; 180 is this project's
  number
- `complexity`: max 3 — this is what rules out a second `if` stacked inside
  the same block
- `max-depth`: 4 · `max-nested-callbacks`: 3
- `react/function-component-definition`: arrow functions only
- `unicorn/filename-case`: PascalCase components, kebab-case for
  `app/**/{page,layout,loading,error,not-found}.tsx`, camelCase `use*.ts`
- `no-secrets/no-secrets`: error
- `no-unused-vars`: error, `_`-prefixed arguments exempt
- `camelcase` with `properties: always`

UI is **shadcn components**. `src/components/ui/*` is generated by the CLI and
never hand-edited — wrap it or pass a className at the call site.

## Security — front-end scope, still non-negotiable

- Admin API calls go through a **route handler or server component**, never
  straight from a client component. An admin token must never reach the
  browser bundle or a network tab on a candidate page.
- Applicant and admin tokens stay in separate storage keys. They already do:
  `src/lib/api/core/tokens.ts`.
- No secret in `NEXT_PUBLIC_*`. That prefix is public by definition.
- `/admin/**` is gated server-side. A hidden nav link is not access control.
- Applicant PII — register numbers, CVs, family and education records — is
  never logged, never sent to a third party, never put in a URL.

## Open decisions — answer these two first

**1. The date is four days away.**
The brief says 2026-09-15. Today is 2026-09-11. Landing plus careers plus a
new admin area plus first contact with a live backend is not four days of
work. Either this is a demo milestone with a narrower done-list, or the date
moves. Pick one and write it into the sentence above.

**2. The admin API does not cover half of what the brief asks for.**
`Recruitment_API_Endpoint_Reference.docx` documents 117 endpoints. Exactly
**14** accept an admin login, and all 14 are content management:

```
POST /api/system/saveCompanyInfo        GET /api/system/getCompanyInfo
POST /api/system/saveRecruitmentSlider  GET /api/system/getRecruitmentSlider
POST /api/system/saveRecNews            GET /api/system/getRecNews, getRecNewsId
POST /api/system/saveRecVideo           GET /api/system/getInternshipImages
POST /api/system/saveInternshipPage     GET /api/system/downloadImage/{filePath}
POST /api/system/deleteInternshipImage  GET /api/applicant/getPositionsDropdown
POST /api/system/uploadImage
```

There is **no documented endpoint** for:

- creating, editing or closing a job posting (recruitment order)
- departments
- accepting or declining an application

So "HR can manage everything about careers" cannot be built as stated. Either
those endpoints exist and are missing from the doc, or the backend team has to
add them. Ask before any admin work starts — building screens against
endpoints that do not exist is the most expensive possible mistake here.

## Known risks

1. **The real backend has never been called.** Everything runs against the
   mock in `src/app/api/applicant/**`. First contact is the riskiest moment in
   this cycle.
2. **No error path.** `listJobs` throws where `listJobsSafe` catches — with a
   live origin, an outage takes `/careers` down as it did on 2026-09-10.
3. **Applicant PII has no owner.** Who may read CVs and register numbers, and
   for how long, is undecided.
4. **No analytics.** Nothing tells us whether anyone finishes the flow.
